Ordinary recursive clones reproduce the committed gitlink, not a moving upstream

## Registered layout only

This branch supports v1.25 and newer registered consumers using
azurefactory/register.json. No legacy aifactory configuration layout, copied
infra-* pipeline entry points, automatic migration or v1.24 execution is supported.
An earlier provisional branch used legacy compatibility; this corrects that choice.

BLUE delegates initialization/refresh to PURPLE's registered_setup.py, the
implementation behind 01-start-v125-and-above.sh. The empty register contains zero
factories and no invented tenant, project, binding or deployed-resource records.
The required registered shell/CLI/helper bundle is installed without replacing
existing catalog configuration or starting Azure operations.

## Repository onboarding and safety

- Full GitHub mirror to an explicitly new/empty destination; configuration-only
  reruns never repeat repository initialization.
- GitHub native template route includes all branches, then selects release/v1.25
  in the consumer; template metadata/gitlink inspection and repair are documented.
- Empty Azure DevOps repositories can initialize the registered catalog and
  pinned helper bundle. Provider execution has a documented upstream limitation.
- Shared .env parsing and GitHub OIDC identity settings, selected-environment
  validation, duplicate detection, redacted dry-run and omitted-secret preservation.
- No dummy AZURE_CREDENTIALS, force-push, orphan-history replacement, checkout
  deletion, automatic editor launch or credentials in Git remote URLs.
- Linux/Windows Git Bash source and local-Git tests; Windows long-path support
  is configured before recursive submodule checkout.
- Exact-SHA successful push-run evidence is required before release publication.

## Shared capabilities and upstream limitations

Infrastructure, API clients, Agent Factory, ML Factory, governance, gateway,
dashboard and health-model implementations are available through the submodule,
not newly implemented in BLUE. Registered configuration and execution depend on
the compatible external Factory API and its exposed runtime contracts.

The scoped GitHub lifecycle template requires OIDC and protected reviewed input.
Service-principal credential fallback is not supported by this registered provider
at the selected pin; BLUE does not introduce a competing deployment workflow.

The scoped Azure DevOps runtime still requires aifactory/pipelines/factory-lifecycle.yml,
while the registered initializer rejects a root aifactory directory. BLUE does not
reintroduce the legacy folder or invent a compatible replacement path. Registered
ADO local initialization is available; scoped provider publication/execution requires
a separately reviewed upstream contract fix and compatible source selection.

The selected upstream also documents an integrated access-hub deployment limitation.
Do not bypass it by switching to legacy scripts or silently selecting another topology.

See the compatibility matrix, three onboarding routes and update guidance:
https://github.com/Azure/enterprise-scale-aifactory/blob/release/v1.25/documentation/bootstrapping.md

## Prerequisites and upgrade

Git, Bash and Python 3.10+ are required. GitHub operations require GitHub CLI,
appropriate repository permissions and organization SSO authorization where applicable.
Registered catalog operations require an approved compatible Factory API; no GUI
or Azure deployment is needed merely to initialize the repository.

Preserve legacy/v1.24 consumers separately; use explicit upstream reviewed migration
or a new registered repository, not a folder rename or destructive bootstrap rerun.
Later v1.25+ pins require a compatible reviewed BLUE update and deliberate gitlink commit.

Native GitHub template generation has not been live-tested with a disposable remote.
The repository-level is_template setting requires administrator action and is not
changed by this code. All-branches generation and the consumer default-branch policy
are necessary while BLUE main remains unchanged.

No Azure deployment was performed. Configuration availability and local tests are
not deployment proof. Optional services and deletion remain explicitly reviewed;
disabling a flag does not necessarily remove existing resources or ongoing costs.
